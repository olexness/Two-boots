## ℹ️ О проекте

### 🎯 Чего мы хотим добиться

Цель проекта — разработать и реализовать современную социальную сеть для киноманов, обеспечивающую:

- удобный доступ к информации о фильмах и сериалах;
- возможность оценивать контент и писать посты;
- формирование персональных подборок («Избранное», «Желаемое»);
- подписки и взаимодействие с другими пользователями;
- простой и безопасный интерфейс для общения и рекомендаций.

### ⚡️ Мотивация (актуальность)

На данный момент отсутствует специализированная социальная сеть, ориентированная именно на киноманов. Существующие крупные площадки либо слишком общие, либо не предоставляют полноценных инструментов взаимодействия между пользователями именно в контексте кино и сериалов.

Это ограничивает возможности обсуждения фильмов, поиска рекомендаций, ведения собственных списков и обмена опытом. Поэтому разработка социальной сети для киноманов является актуальной задачей.

### 📌 Назначение проекта

Проект предназначен для разработки онлайн-платформы — социальной сети для киноманов. Система предоставляет пользователям возможность обмениваться информацией о фильмах и сериалах, оставлять посты-рецензии, формировать подборки («Избранное», «Желаемое»), просматривать профили других пользователей и взаимодействовать с сообществом любителей кино.

Система представляет собой веб-платформу, предназначенную для поиска фильмов и сериалов, ведения списков рекомендаций, публикации постов, просмотра профилей пользователей и взаимодействия внутри сообщества. Платформа позволяет собирать подборки, получать рекомендации и обмениваться мнениями о просмотренных проектах.

Платформа должна стать востребованной среди аудитории за счёт удобства, безопасности, интуитивного интерфейса и наличия функций, которых нет в существующих сервисах.

### Похожие проекты

- **Letterboxd** — социальная платформа для киноманов с рецензиями, оценками и списками;
- **IMDb** — крупная база данных фильмов и сериалов;
- **Кинопоиск** — сервис с карточками фильмов, рейтингами, подборками и рекомендациями.

### Прямые конкуренты

1. **Letterboxd**

Сильные стороны:
- ориентирован на киноманов;
- позволяет вести списки, рецензии и оценки;
- формирует тематическое сообщество.

Слабые стороны:
- ограниченные социальные механизмы по сравнению с полноценной социальной сетью;
- слабая кастомизация пользовательского взаимодействия;
- акцент скорее на дневнике просмотров, чем на полном сообществе.

2. **Кинопоиск**

Сильные стороны:
- крупная база данных о фильмах и сериалах;
- развитая система рейтингов и рекомендаций;
- узнаваемость и большая аудитория.

Слабые стороны:
- основной акцент сделан на каталог и медиасервис;
- социальное взаимодействие пользователей выражено слабо;
- сообщество не является центральной частью системы.

3. **IMDb**

Сильные стороны:
- огромная база данных фильмов, сериалов и актёров;
- авторитетность и узнаваемость.

Слабые стороны:
- ограниченное социальное взаимодействие;
- платформа ориентирована в первую очередь на информационный каталог, а не на пользовательское сообщество.

### Вывод

Существующие социальные сети — Facebook, Instagram, Twitter и YouTube — универсальны и не учитывают специфические потребности киноманов. В них отсутствуют специализированные подборки фильмов, механизм рекомендаций с учётом истории просмотров, интеграция с тематическими базами и удобная навигация по кинематографическому контенту.

Специализированные решения, такие как Letterboxd, IMDb и Кинопоиск, закрывают лишь часть потребностей пользователя. Two-boots должен объединить в одной системе функции социальной сети, кино-каталога, пользовательских подборок и основы персонализированных рекомендаций.

### Основные пользователи

* конечный пользователь (киноман);
* автор контента (пишет посты и рецензии);
* подписчики;
* гости (неавторизованные пользователи);
* администратор / модератор платформы.

### Внешние участники и системы

**Контекстный уровень:**
* **пользователь через веб-браузер** — основной внешний участник, показанный на текущей контекстной диаграмме.

**Архитектурный уровень:**
* **TMDb API** — внешний источник данных о фильмах и сериалах;
* **сервер авторизации** — внешний или выделенный компонент проверки учётных данных, если авторизация не реализована внутри backend-приложения.

### Ограничения
* передача данных осуществляется только по HTTPS;
* доступность платформы — не менее 95%;
* время загрузки ограничено техническими требованиями;
* часть функций зависит от доступности внешнего API TMDb.

# Функциональные требования

1. Система должна предоставлять пользователю возможность зарегистрироваться, указав имя, логин, пароль и фото профиля.
2. Система должна предоставлять возможность авторизоваться по логину и паролю.
3. Система должна обеспечивать поиск фильмов и сериалов по названию.
4. Система должна предоставлять пользователю возможность получать случайный фильм или сериал.
5. Система должна отображать подробную информацию о выбранном фильме или сериале.
6. Система должна предоставлять возможность добавлять фильмы в «Избранное» и «Желаемое» и удалять их.
7. Система должна отображать списки «Избранное» и «Желаемое».
8. Система должна предоставлять возможность написания, просмотра и публикации постов.
9. Система должна предоставлять возможность просмотра профиля другого пользователя, включая его посты и подборки.
10. Система должна позволять подписываться на других пользователей и отписываться.
11. Система должна сохранять историю действий пользователя для дальнейшей персонализации.
12. Система должна обеспечивать базовую модерацию пользовательского контента.

# Нефункциональные требования

1. Гибкий и удобный пользовательский интерфейс, обеспечивающий комфортную работу на различных устройствах, включая мобильные.
2. Высокая производительность платформы, при которой приложение должно загружаться на смартфонах менее чем за 5 секунд, а страницы — не более чем за 6 секунд при скорости соединения 1 МБайт/с.
3. Надёжная защита данных пользователей посредством использования протокола HTTPS.
4. Высокая доступность платформы с обеспечением работоспособности не менее чем 95% времени и средним временем между отказами не менее 30 дней.
5. Быстрое восстановление системы в случае сбоя, при котором не менее 70% неисправностей устраняются в течение 5 минут.
6. Масштабируемость и гибкость архитектуры, позволяющие выдерживать увеличение нагрузки и объёма данных без потери качества работы.
7. Расширяемость модулей для последующего внедрения рекомендательной системы.

# Основные бизнес-процессы

### Регистрация и авторизация пользователя

**Действующие лица:** пользователь, система Two-boots, сервер авторизации.  
**Когда выполняется:** при первом входе или авторизации пользователя.  
**Шаги / Действия:**
- пользователь вводит регистрационные данные или логин и пароль;
- система проверяет корректность введённых данных;
- система создаёт учётную запись или выполняет вход;
- сервер авторизации подтверждает права доступа, если авторизация вынесена во внешний компонент;
- система предоставляет пользователю доступ к персонализированным функциям.

**Результат:** пользователь входит в систему.

### Поиск фильма и просмотр карточки

**Действующие лица:** пользователь, система Two-boots, TMDb API.  
**Когда выполняется:** при вводе поискового запроса.  
**Шаги / Действия:**
- пользователь вводит запрос;
- система проверяет корректность запроса;
- система получает данные о фильмах из TMDb API;
- система отображает результаты поиска;
- пользователь открывает карточку фильма.

**Результат:** пользователь получает информацию о фильме и взаимодействует с системой.

### Формирование подборок

**Действующие лица:** пользователь, система Two-boots.  
**Когда выполняется:** при добавлении фильма в «Избранное» или «Желаемое».  
**Шаги / Действия:**
- пользователь выбирает фильм;
- пользователь выбирает нужную подборку;
- система сохраняет фильм в выбранной подборке;
- система обновляет данные подборки пользователя.

**Результат:** подборка пользователя обновлена.

### Публикация постов

**Действующие лица:** пользователь, система Two-boots, модератор.  
**Когда выполняется:** при создании нового поста или рецензии.  
**Шаги / Действия:**
- пользователь вводит текст поста;
- система проверяет заполненность и корректность данных;
- система сохраняет пост;
- система отображает публикацию другим пользователям;
- модератор может проверить публикацию при наличии жалобы или нарушения.

**Результат:** в системе появляется новый пользовательский контент.

### Подписка на пользователей

**Действующие лица:** пользователь, система Two-boots.  
**Когда выполняется:** при просмотре профиля другого пользователя.  
**Шаги / Действия:**
- пользователь открывает профиль другого пользователя;
- пользователь нажимает кнопку подписки или отписки;
- система создаёт или удаляет связь между пользователями;
- система обновляет списки подписок и подписчиков.

**Результат:** формируется социальное взаимодействие между пользователями.

### Персонализация контента

**Действующие лица:** пользователь, система Two-boots.  
**Когда выполняется:** при накоплении достаточной истории действий.  
**Шаги / Действия:**
- система учитывает просмотры, подборки и поисковые запросы пользователя;
- система формирует профиль интересов пользователя;
- система использует профиль интересов для ранжирования контента.

**Результат:** пользователь получает более релевантные рекомендации.

## Описание сценариев использования

### Ключевой сценарий использования

### UC-01: Поиск фильма и просмотр карточки

**Действующие лица (Actors):**
* Пользователь;
* TMDb API — внешний источник данных, участвующий в сценарии как вспомогательная внешняя система.

**Рассматриваемая система:**  
Two-boots.

**Триггер:**  
Пользователь вводит название фильма, актёра или жанра в строку поиска.

**Предусловия:**
* пользователь авторизован в системе;
* система Two-boots доступна;
* внешний API TMDb доступен и отвечает корректно.

**Основной поток событий:**
1. Пользователь вводит поисковый запрос.
2. Система проверяет корректность запроса.
3. Система запрашивает данные во внешнем источнике TMDb API.
4. TMDb API возвращает список фильмов с метаданными.
5. Система преобразует полученные данные к формату, используемому внутри Two-boots.
6. Система отображает пользователю список найденных фильмов.
7. Пользователь выбирает конкретный фильм.
8. Система получает подробную информацию о выбранном фильме.
9. Система отображает пользователю карточку фильма.
10. Система сохраняет факт просмотра карточки в истории взаимодействий для дальнейшей персонализации.

**Альтернативные потоки:**
- 4а. Если TMDb API недоступен, система показывает сообщение о временной недоступности поиска и использует кешированные данные, если они есть.
- 1а. Если пользователь ввёл пустой или некорректный запрос, система не выполняет поиск и предлагает ввести корректное название фильма.
- 8а. Если информация о выбранном фильме недоступна во внешнем источнике, система показывает сообщение об ошибке и предлагает альтернативные фильмы.

**Постусловия:**
* пользователь ознакомился с подробной информацией о фильме;
* история взаимодействий пользователя обновлена;
* система может использовать сохранённые данные при персонализации.

**Используемые данные:**

| Сущность данных | Назначение в сценарии |
| --------------- | --------------------- |
| `UserProfile` | идентификатор пользователя, настройки профиля и признаки авторизации |
| `SearchQuery` | поисковый запрос пользователя |
| `MovieData` | данные фильма, полученные из TMDb API или кеша системы |
| `InteractionHistory` | факт просмотра карточки и другие действия пользователя |

**Архитектурная привязка сценария:**

| Модуль | Участие в сценарии |
| ------ | ------------------ |
| Модуль пользовательского интерфейса | принимает поисковый запрос и отображает результаты |
| Модуль поиска | проверяет запрос и управляет поисковым сценарием |
| Модуль интеграции TMDb API | получает данные из внешнего источника |
| Модуль карточки фильма | подготавливает подробную информацию о выбранном фильме |
| Модуль истории взаимодействий | сохраняет факт просмотра карточки |
| PostgreSQL | хранит историю взаимодействий и кешированные данные при необходимости |

**Связь с требованиями:**
* FR-3 — поиск фильмов;
* FR-5 — отображение карточки фильма;
* FR-11 — сохранение истории действий пользователя.

**Обоснование характеристик:**
* Производительность: запрос к TMDb API должен обрабатываться быстро, часть данных может кешироваться.
* Надёжность: при проблемах с TMDb API система должна уметь работать в ограниченном режиме.
* Безопасность: запрос к TMDb API выполняется через серверную часть системы, чтобы не раскрывать ключ внешнего API на стороне клиента.

## Описание сценариев ошибок

### Ошибка №1: Недоступность TMDb API

**Условия возникновения:**
* внешний источник TMDb API не отвечает;
* получен ответ 429, 500 или 503;
* ключ API утратил валидность или исчерпан лимит запросов.

**Реакция системы:**
1. Система фиксирует ошибку в журнале событий.
2. Система сообщает пользователю о временной недоступности поиска.
3. Система использует кешированные данные, если они есть.
4. Пользователь может продолжить навигацию по сохранённым или популярным фильмам.
5. Администратор получает диагностическую информацию через механизм мониторинга.

**Сообщение пользователю:**  
**«Поиск временно недоступен. Показаны результаты из кеша.»**

**Постусловия:**
* пользователь уведомлён о проблеме;
* функциональность частично сохранена через кеш;
* ошибка зафиксирована для последующего анализа.

**Влияние на архитектуру:**
* необходим модуль кеширования запросов TMDb API;
* требуется fallback-логика выдачи популярных фильмов;
* требуется журналирование ошибок внешней интеграции.

### Ошибка №2: Некорректный поисковый запрос пользователя

**Условия возникновения:**
* пустая строка запроса;
* ввод только спецсимволов;
* запрос превышает максимально допустимую длину.

**Реакция системы:**
1. Система проверяет запрос до выполнения поиска.
2. Система не обращается к TMDb API при некорректном запросе.
3. Пользователь получает подсказку о необходимости изменить запрос.
4. Событие не фиксируется как системная ошибка, кроме debug-режима.

**Сообщение пользователю:**  
**«Введите корректное название фильма.»**

**Постусловия:**
* внешний API не получает некорректный запрос;
* пользователь получает понятную подсказку.

**Влияние на архитектуру:**
* требуется модуль валидации пользовательского ввода;
* проверка должна выполняться на уровне пользовательского интерфейса и на серверной стороне системы.

### Ошибка №3: Недоступность серверной части Two-boots

**Условия возникновения:**
* серверная часть системы не отвечает;
* возник сбой базы данных;
* система перегружена.

**Реакция системы:**
1. Пользователь получает сообщение о временной недоступности платформы.
2. Система фиксирует ошибку в журнале событий, если серверная часть доступна для записи логов.
3. Система мониторинга отправляет уведомление администратору.
4. До восстановления работы операции пользователя не выполняются.

**Сообщение пользователю:**  
**«Сервис временно недоступен. Попробуйте позже.»**

**Постусловия:**
* пользователь предупреждён;
* действия пользователя не выполняются до восстановления системы.

**Влияние на архитектуру:**
* требуется мониторинг доступности серверной части;
* желательно предусмотреть fallback-экран на стороне пользовательского интерфейса;
* требуется обработка ошибок соединения.

### Ошибка №4: Фильм недоступен в TMDb

**Условия возникновения:**
* TMDb API возвращает 404 для конкретного фильма;
* данные фильма были удалены или помечены как недействительные.

**Реакция системы:**
1. Система обрабатывает ответ внешнего источника как структурированную ошибку.
2. Система сообщает пользователю, что информация о фильме недоступна.
3. Система предлагает альтернативные фильмы из той же категории, если такие данные доступны.
4. Запрос фиксируется в журнале как обращение к устаревшему или недоступному идентификатору фильма.

**Сообщение пользователю:**  
**«Информация о фильме недоступна.»**

**Постусловия:**
* пользователь получил уведомление;
* система предлагает замену при наличии альтернативных данных.

**Влияние на архитектуру:**
* в модели данных нужен признак недействительного внешнего идентификатора фильма;
* требуется механизм обновления устаревших данных;
* требуется обработка ошибок внешнего источника.

### Ошибка №5: Превышен лимит запросов TMDb

**Условия возникновения:**
* TMDb API возвращает HTTP 429;
* за короткий промежуток времени выполнено слишком много запросов.

**Реакция системы:**
1. Система фиксирует превышение лимита запросов.
2. Система временно ограничивает повторные обращения к TMDb API.
3. Пользователь получает сообщение о необходимости повторить попытку позже.
4. Система использует локальный кеш популярных фильмов, если он доступен.

**Сообщение пользователю:**  
**«Слишком много запросов. Попробуйте позже.»**

**Постусловия:**
* пользователь видит fallback-данные при их наличии;
* лимит внешнего API не расходуется повторно;
* событие фиксируется для последующего анализа.

**Влияние на архитектуру:**
* нужна локальная база популярных фильмов или кеш ответов;
* требуется throttling / rate-control механизм;
* требуется единая обработка ошибок внешнего API.
